# Application repair during an authorized update

The updater derives its versioned `system-files-v1` software structure from the integrity-checked package and reviewed application catalog. Package put entries define required software bytes and parent directories. Required unpackaged JavaScript, CSS and HTML must already exist; pinned vendor libraries must match `distribution/dependencies.json`. Other catalog entries are optional. Unknown files are preserved. Neither a missing private Workspace nor missing dealership records are recreated.

The normal software-only path is **Checking → Repairing → Verifying → Ready** after the user authorizes the update. It restores missing approved application directories and scripts, replaces damaged package files, and can regenerate an absent origin compatibility index from verified HTML and the named root launcher from reviewed canonical software bytes. Unknown contents at the named launcher are preserved and stop automatic repair. It preserves the selected installation's private Workspace, original reports, settings, manual edits and unrelated files. It never invokes Fresh Installation. Missing application entry HTML without a recognized clean-install software manifest, an unrecognized root, an interrupted Fresh marker, missing private Workspace, damaged unpackaged software or denied permission stop the update with a local action required.

Backups and journals remain in `System Files/Workspace/backups/system-updates`. Before application mutation, the updater writes and reads back a local `System Files/MOONDOG_UPDATE_IDENTITY.json` identity. New recovery journals bind to that identity. Copied journals from another initialized installation are refused, even if both stores have overlapping synthetic identifiers and identical software versions. Identity changes during execution stop further writes and retain recovery evidence. The identity is local software recovery metadata, never an operational-data authority and never uploaded. A complete cloned installation also clones this identity; this is not proof of a unique physical device.

The updater rechecks selected folder relationships using the native File System Access API `isSameEntry` (unavailable identity verification fails closed), permissions, the private boundary and recovery identity around mutations. It verifies original bytes after backing up, hashes written files, verifies package-required directories, and records the package digest, schema, version and completion only after readback. Opening a write stream retries at most three times for recognized transient synchronization failures, before any bytes are written. Permission denial is never retried as a transient failure. A failed write or close is never blindly retried and restores verified originals. Failed rollback retains an applying journal; a newly loaded updater can perform the existing explicitly confirmed recovery action using the verified backup. Legacy journals without an installation identity require local support review; they are not silently assigned to the currently selected store.

Within one runtime, conflicting update and recovery attempts return busy. Web Locks also coordinate tabs of the same browser origin when available. These mechanisms **do not provide distributed locking** against other devices, other origins, external programs or OneDrive. Do not run simultaneous updates to a synchronized installation on separate devices. Permission loss or an unresolved journal is a stop condition, never permission to retry indefinitely. No cross-device atomicity is claimed.

If the installed application cannot start, first preserve the entire existing installation and its Workspace. Download the self-contained `repair-moondog.html` from reviewed main using GitHub's Download raw file action and open it locally in Edge. It does not depend on the damaged installation's scripts or third-party libraries to start. Choose the parent installation folder, then authorize the verified Beta software repair. A recognized `INSTALLATION-MANIFEST.json` permits safe restoration of missing entry HTML, app directories, scripts and launcher; missing private Workspace remains a blocker. The page downloads only manifest/package software and never uploads local records.

If that page cannot recognize or access the installation, preserve it for local review. Obtain the current verified clean-install ZIP through the repository's documented distribution, verify its checksum, and extract it to a separate directory. Open its launcher as an independent clean application. Do not extract over the damaged copy, choose Fresh, copy recovery journals across installations, or replace missing operational files with empty files. Recover existing operational data only through the established local recovery/backup workflow with the correct folder permission. Publication cannot grant that permission or operate the local device remotely.

## Evidence and remaining acceptance

`tests/self-heal-update-directories.test.cjs` executes the actual updater and plan with Node Web Crypto and synthetic File System Access fixtures. It covers missing directories/scripts, corrupted application bytes, absent origin page and named launcher, bounded transient stream-opening locks, rollback, fresh-runtime recovery after failed rollback, unknown-file preservation, denied/read-only permission, wrong selected root, two stores with identical synthetic private fixture bytes, copied rollback journal rejection, concurrent attempts, browser lock denial, identity tampering, invalid/pending journals, tampered packages, missing unpackaged dependency, repeated updates and protected originals. `tests/install.test.cjs` retains the existing installer and bounded recovery-inventory regressions; runtime mirrors remain byte-identical.

This is scoped synthetic proof. Full exact packaged-head CI, trusted packaging, protected review, merge and public manifest/package checks remain required. Physical Edge, Windows and OneDrive are not proven by these tests. General legacy-layout migration, automatic restart recovery without the existing confirmation, distributed writers, repair of unstartable copies without a recognized software identity, restoration of missing unpackaged vendor bytes, and physical-device use of the standalone page remain unimplemented or unproven. Issue #797 must remain open for those acceptance gaps. No real store installation is claimed.

The standalone page includes exact copies of `updates/verify.js`, `updates/package-plan.js`, `updates/apply-design-model.js` and `updates/install.js`, escaped only to prevent embedded closing script tags. Its catalog mirrors the reviewed runtime catalog. `tests/recovery-page.test.cjs` blocks stale module/catalog copies and exercises the actual standalone controller with real Web Crypto and isolated filesystem writes, including cancellation, tampering, wrong roots, permission denial and preservation. Keep these copies synchronized when changing canonical updater source. Publication still requires the source PR's protected review and verified main integration.
