# Direct ChatGPT engineering

During an active ordinary ChatGPT conversation, The repository owner can give MoonDog an engineering objective such as “Fix this issue and finish it” or “Continue MoonDog.” Use connected GitHub tools to inspect current main, relevant source, open work, authorization and exact-head evidence; implement the smallest change on a branch; open or update its PR; inspect automatic CI; correct failures; let eligible changes merge; then independently verify main and the public Beta manifest/package digest. A local checkout is optional tooling. No separate coding agent, Work session, external reviewer, manual CI dispatch or owner status relay is part of the routine repository contract.

This describes capabilities actually available through the connected GitHub interface: source/diff reads, branches, trees, commits, expected-head ref updates, PRs, CI results, review submission and authorized merge. A repository cannot grant tools absent from a particular ChatGPT session. If an operation is unavailable, state the exact missing capability and continue independent work. Never claim a shell or interactive device browser is available merely because GitHub CI can run Node and Chromium.

## Automatic verification and release

One owner objective covers eligible routine implementation, testing, corrective commits, PR creation and qualifying Beta publication under standing authorization. GitHub events start the tests, trusted same-PR packaging and guarded merger. The packaging workflow owns version reservations and adds a package only when runtime parity requires it. Obsolete heads cannot satisfy current-head checks. Branch updates use an expected-head lease and preserve concurrent work.

The workflow reads its verification classifier from the immutable base commit. Its complete tree diff includes both sides of a rename and refuses narrower verification for unknown inputs, executable files, symlinks, submodules, changed test logic, policy, dependencies or shared runtime. A new or missing classifier runs the full path; a PR cannot use its own classifier changes to reduce its bootstrap proof.

| Change class | Required functional proof |
|---|---|
| Non-policy Markdown only | Publication/source/package contracts and boundary tests; no unrelated full suites, vendor downloads, ZIP builds or browser navigation |
| Beta metadata with unchanged source, tests, dependencies and Stable | Package/publication contracts, deterministic clean-install ZIP, extracted browser smoke and actual verified Beta installation; no repeated full UX matrix |
| UI/shared application code, imports, calculations, persistence, recovery, backups, updates, unknown scope | Focused production-path regressions first, then every remaining Node test once, full Python suite and complete applicable packaged browser/install/rollback/preservation proof |
| Security and protected automation | Full bootstrap proof and separately authorized exact-head protected review; these controls cannot automatically approve themselves |

Both full-history scanners and current-tree publication scanning remain mandatory. The independent scheduled/public-surface audit retains releases, artifacts, discussions, all refs and redacted findings. No history result is reused solely because a commit SHA matches: advertised refs and scanning rules may have changed. An authenticated, complete, equivalent object-level proof cache has not been established, so full history remains enforced. The two different history scanners run independently after functional/publication boundaries pass, and the required `Publication Check` succeeds only when every required job succeeds. Failed, cancelled, skipped or missing results block it.

Cached distribution libraries are keyed by reviewed dependency/build inputs and rehashed against every selected library's SHA-256 pin before entering either deterministic ZIP. A corrupt cache blocks the build; cached bytes never count as passing verification. Superseded PR browser runs are cancelled; manual proofs keep independent concurrency groups.

## Protected decisions and limits

Protected updater, security, release control, policy and critical preservation-test changes retain the documented exact-head owner review/bootstrap. Prepare the complete diff and passing evidence, then request the one required decision. An approval for an older head is not approval for a replacement. Standing authorization does not permit weakening branch protection, bypassing privacy findings or having a workflow merge its own controls. Routine eligible work needs no Codex, independent AI or owner review metadata.

Stable promotion, destructive operations, real-store installation and access to private Workspace require their separate authorization. Tests use synthetic data. Successful CI or a public package does not establish installation on a local device. Ordinary ChatGPT acts during its active execution session; GitHub Actions provides bounded verification/release automation, not indefinite background implementation.
